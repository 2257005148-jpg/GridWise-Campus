## 3. 模型与 GUI 一致性审查 / Model and GUI consistency

**已静态确认 / Statically verified**

- `peak_cap_kw=None` 时不创建新约束，目标仍为 `Σ grid_kw × price × step_hours`；默认模型家族、无额外策略字段和格式 1 清单分支保留。
- 显式上限先经过 GUI 有限非负数值检查、控制层 `grid_max_kw` 检查、核心 `_number`/场景上界检查，再形成逐时 `grid[t] <= peak_cap_kw` 约束。
- 基线仍调用 `solve(..., with_battery=False)`，没有传入峰值上限；因此与优化方案共享输入、时间步和电价，但不伪装成受 55 kW 约束的基线。
- 求解器必须同时返回 `SolverStatus.ok` 和 `TerminationCondition.optimal`；否则 CLI 非零退出、运行目录不产生可信 `COMPLETE`，GUI 清空结果并显示失败。
- GUI 三项指标来自安全读取后的 `prepare_visualization_data`，没有在 Tk 层重新实现公式或硬编码业务结果。测试/烟测中的 55、131.011… 等数值仅是断言和合成演示。
- 成本参考绑定相同场景原始字节摘要、求解器名称、规范化 `core.py` 摘要，并重新安全读取且与当前导入 CSV 对齐；缺少参考时不展示差额。

## 4. 产物与独立审计审查 / Artifacts and independent audit

- 默认模式保留格式 1 和六个原元数据字段；峰值模式使用格式 2，并严格增加 `optimization_mode="peak_cap"` 和有限非负 `peak_cap_kw`。
- CLI 汇总、manifest 和安全读取器逐项比较策略元数据；`scenario_sha256` 继续绑定场景原始字节。
- 独立审计器不调用 Pyomo，继续检查输入回显、功率平衡、SOC 递推、效率、上下界、互斥、终端 SOC、成本、电量和峰值；峰值模式只对优化方案追加逐时上限复核。
- 发布顺序仍是求解→独立审计→审计前后文件摘要比较→manifest→内部复核→发布→`COMPLETE`→安全重读；未见通过放宽既有容差实现兼容的修改。
- 老的格式 1 结构仍由读取器和当前默认运行覆盖；更早提交生成且模型摘要不同的旧产物仍应使用历史上下文审计，当前文档对此有明确限制。

## 5. 桌面稳定性审查 / Desktop stability

- 后台线程只执行控制层操作并向队列写结果；所有控件更新均在 Tk `after` 驱动的 `_poll()` 主线程路径中。
- 运行时模式控件和上限输入禁用；重复运行由 `_active_kind` 拦截。
- 输入/目录变化及取消使用 cancel event 和 generation 隔离；迟到结果因 generation 不匹配被丢弃，关闭窗口等待 `_pending_jobs` 清空后销毁。
- 历史加载先重新安全读取，再与当前 CSV 对齐；策略元数据来自已校验 manifest/summary，程序化恢复时用 `_updating_policy` 避免触发失效回调。
- 未发现 v0.3.12 引入额外 `Tk()` 根解释器、后台线程直接改控件或无限重试。
- 历史 Tk/Tcl 焦点与资源读取间歇异常的根因仍为 `UNKNOWN`；本次组合审查没有把 Quota Float 卸载解释为修复证据。

### 低风险与证据缺口 / Low-risk gaps

1. **成本参考不是“完全相同运行环境”证明。** 当前匹配 `scenario_sha256`、`solver_name`、模型源码摘要和当前 CSV，但不要求 `solver_version`、`dependency_lock_sha256`、Git commit 或 source state 相同。这足以约束相同数学输入与核心模型，不足以宣称环境逐字可复现。UI 和文档目前只称“同输入有效对照”，没有声称同环境；因此不是提交阻断项。若未来提高措辞或复现要求，应追加环境字段匹配。
2. **旧格式动态证据是“当前代码生成的格式 1”。** `test_default_immutable_run_retains_v1_manifest_and_audit` 证明默认分支、格式和数值回归；它不是冻结的 pre-v0.3.11 历史产物夹具。文档已说明历史模型摘要不同应进入历史审计上下文，因此不是兼容性虚报，但仍是证据边界。
3. **策略切换中的并发保护主要依赖控件禁用。** 正常 GUI 路径无法在任务运行时更改模式；若内部代码直接写 `StringVar`，`_policy_changed` 会取消并使该代结果失效，但可能在旧工作线程清理结束前允许新任务。现有 generation 与 pending-job 机制可避免旧结果覆盖和关闭遗漏；没有直接用户路径，也没有专门的“运行中程序化改模式”测试。
4. **严格防御顺序可进一步收紧。** `_show_result` 在策略达标断言前先暂存图表和历史标签；若内部控制层违反已审计结果不变量，异常处理会清空画面和改为失败，但该无效条目可能暂留于内存历史。真实发布链由独立审计和安全读取先行，未发现可从文件输入触发该状态；属于防御性测试缺口。
5. Windows 符号链接负向测试因 `WinError 1314` 跳过，不能计为通过。Linux/macOS、托管 CI、原生跨显示器 DPI、屏幕阅读器和长期耐久性仍未执行。
