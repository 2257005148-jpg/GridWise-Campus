## 6. NOTICE 必要性判断

结论：**本阶段不创建 `NOTICE`。**

Apache License 2.0 第 4(d) 节要求：如果被分发的 Work 本身包含 NOTICE，则衍生发行需要传播其中适用的归属信息。Apache 的发行组装指南还强调，LICENSE/NOTICE 应准确反映实际发行内容，只为被捆绑内容处理相应信息，不应把非捆绑依赖加入 NOTICE。

本项目当前定义的发行内容只有项目源代码、测试、文档、合成示例、配置和元数据；没有复制第三方 Wheel、原生二进制或上游 NOTICE。v0.3.32/v0.3.33 也未发现项目源文件中存在经过修改的第三方代码。因此：

1. 没有适用的上游 NOTICE 需要向项目 NOTICE 冒泡传播；
2. BSD/MIT 版权条款保留在第三方清单及其上游许可证中，不需要为了形式重复进一个空 NOTICE；
3. 如果未来发行包含 Wheel、DLL、vendored 源码或上游 NOTICE，必须按**实际捆绑内容**重新审计并创建或更新 NOTICE。

本判断是工程合规准备，不是法律意见。Apache 的“Applying the License”页面面向 ASF 项目时要求其项目带正确 NOTICE；不能据此推导所有非 ASF、没有 NOTICE 内容的个人项目都必须制造空 NOTICE。

## 7. CONTRIBUTING 与治理决定

候选 `CONTRIBUTING.md` 包含：

- Fork、分支、最小改动和 Pull Request 流程；
- Python 3.12+ 与合成数据边界；
- `unit`、`gui`、`integration` 主 Marker 和 `solver`、`audit`、`slow` 风险 Marker；
- collect-only、unit、integration、GUI 及日常安全测试命令；
- `solver` / `audit` / `slow` 只能在维护者明确授权、隔离环境和合成数据下执行；
- 不把 `SKIPPED` 或 `NOT_RUN` 写成通过；
- 第三方来源和许可证披露、不得提交凭据/个人路径/运行产物；
- Apache-2.0 第 5 节对应的贡献许可说明；
- 当前不强制 CLA 或 DCO。

DCO 1.1 适合在项目规模扩大、多人贡献或治理要求增强时考虑；目前个人项目、无共同作者，直接强制 DCO 的收益不足，且签署记录会永久包含贡献者身份信息。CLA 当前也没有明确必要性。本阶段均不引入。

漏洞报告专用邮箱尚未确认，文件使用 `[PROJECT_SECURITY_CONTACT_EMAIL_TO_BE_CONFIRMED]`。该占位符意味着私密邮件渠道**尚不可用**；在维护者配置专用地址或确认 GitHub Private Vulnerability Reporting 已启用前，不能宣称漏洞报告渠道完整可用。
