## 2. 根因与修复 / Root causes and fixes

### P1-01：失效的历史提交 SHA / Stale historical commit SHA

`tests/test_audit_history.py` 仍把净化前提交 `93fe6058a237472483292f2c256045de2c420fdc` 作为真实 Git 对象读取。净化后的等价提交为 `e7d8de5bf494af7ba2c86acd8401b639d82eb7f0`，主题仍为 `Record observed environment and audit run metadata`，并且父关系已在 46 项映射中核实。/ The test still dereferenced the pre-cleanup object. Its verified post-cleanup equivalent is the mapped commit above, with the same subject and verified parent relationship.

修复：

- 将测试常量 `BASE` 更新为净化后的真实提交。
- 审计 `tests/`、`tools/` 和 `docs/` 中的 40 位十六进制字符串；不做盲目全局替换。
- `tools/` 中没有失效的可执行对象引用。
- 对 45 份非受保护阶段报告中的 79 处真实提交引用，按 v0.3.28 的旧→新映射机械更新。
- v0.3.28 映射表和 v0.3.29 的失败证据保留旧 SHA，以维持审计证据含义；除此之外，失效映射 SHA 为 0。

### P1-02：Windows 换行转换破坏字节哈希 / Windows EOL conversion changed hashed bytes

全局 `core.autocrlf=true` 将候选工作树中的 JSON、CSV 和依赖锁文件检出为 CRLF。审计摘要按这些工作树字节生成哈希，而 LF 测试随后复制 Git blob 的 LF 字节，因此产生 `scenario_sha256` 不一致。/ Global `core.autocrlf=true` checked byte-hashed inputs out as CRLF. The summary was hashed from those worktree bytes, while the LF test later copied LF blob bytes, producing a scenario hash mismatch.

修复：新增仓库级 `.gitattributes`，仅约束实际参与字节语义或审计的输入：

```gitattributes
/examples/*.json text eol=lf
/examples/*.csv text eol=lf
/requirements/*.txt text eol=lf
```

未修改任何哈希校验、审计容差或业务算法，也未对所有文本做无差别换行转换。/ No hash check, audit tolerance, or business algorithm was changed, and no repository-wide EOL rewrite was performed.
